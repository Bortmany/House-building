# Estimator — house material quantities

**App:** House-building (not listed in `Agents/docs/apps.md` — the owner chose not to register this app; noted here per instruction, not an oversight to fix).

**Status:** spec only. Recommend `ui-designer` runs on this spec before `builder` starts, to lay out the input form and results screen (phone-first, 390px–1440px per conventions).

## The problem, in the owner's words

"A person is building a house and trying to count how many blocks, steel, ready mix cement is needed to build the house. The input can be the house size, floors, approx number of rooms, floorplan manually. It's a simple website in HTML so I can share it with a colleague."

## What the user sees and does

One page, `index.html`, opened directly in a browser (works from `file://`, no server, no install). Two sections stacked on the same page.

### Section 1 — the estimator (this spec)

**Step 1: Tell it about the house**
- Number of floors (1–4)
- Wall height in metres (2.4–4.5 m, one value applied to every floor)
- Choose one of two ways to describe the layout:
  - **A. Room list (default):** an "Add room" table — each row is a room name, length (m), width (m). User adds/removes rows freely. This is the same list used for every floor (v1 assumes floors repeat the same layout — see open question 1).
  - **B. Quick shortcut:** "I don't want to type rooms — just use approximate size." User enters an approximate house size in m² per floor. The page auto-generates a plausible room list behind the scenes (using the room-mix assumption in `docs/research/assumptions.md`) and shows that generated list to the user, editable, so they can see and correct what was assumed.
- A "Calculate" button.

**Step 2: See the results**
A results panel, grouped by structural element (foundations, columns, beams, slabs, walls). For each element:
- Ready-mix concrete needed, in m³
- Rebar steel needed, in kg and in tonnes
- Concrete blocks needed for walls, split external vs internal, in pcs
- Every quantity has its own **wastage %** shown next to it, pre-filled from the assumptions file, and the user can change it — changing it recalculates instantly.

Below the element breakdown, a **total cost in OMR**, built from an editable price table (price per block, per tonne of rebar, per m³ of ready-mix, etc.). Every price row shows:
- The default value
- A "last checked" date and a source note (both come from `docs/research/assumptions.md`)
- An input the user can overwrite; overwriting it changes the total immediately

A visible line above the price table: **"These are starting-point prices, not quotes — check with your supplier."**

If the user enters something invalid (e.g. a room 0 m wide, 6 floors), the page shows a plain-English message next to that field ("Wall height should be between 2.4 and 4.5 m") — never a blank result or "NaN".

### Section 2 — "How this page was built"

Already scoped and out of this spec's concern: a read-only section, generated by the build script from `docs/build-log/*.json`, showing the agent team's steps. This spec only notes that it exists on the same page; the estimator does not read from or write to it.

## Out of scope (v1)

- Floorplan upload (image, PDF, DWG) — explicitly deferred by the owner.
- Finishes: plaster, tiles, paint.
- MEP (electrical, plumbing, HVAC).
- Labour cost or labour time.
- Any claim, disclaimer wording aside, that prices are accurate or a substitute for a supplier quote.
- Arabic / bilingual UI — English only per the owner's decision.
- Saving/loading projects, accounts, sharing links — this is a stateless single-page calculator; nothing persists between visits.
- Choosing the construction system in the UI — it is fixed by the assumptions file the researcher writes, not user-selectable in v1.

## Data touched

No server, no database, no accounts — everything lives in the browser tab and disappears on reload. In plain terms:

- **What the user types:** floors, wall height, room list (or approximate m² shortcut), any wastage % or price overrides. None of this is sent anywhere or saved anywhere; it only exists on the visitor's own screen while the page is open.
- **What ships with the page:** the construction assumptions and default prices researched in `docs/research/assumptions.md`, baked into the page at build time (`src/calc.js`'s `DEFAULTS`).
- **What is never collected:** no name, email, location, or any personal detail — the page doesn't ask for one.

## Privacy / rate limiting / core guarantee (engineering standards check)

- **New personal data?** No. Nothing typed into this page leaves the browser or touches a server — there is no server. No privacy page change is needed.
- **Rate limiting / external calls?** None. `estimate()` is a pure, local, offline calculation with no network or paid API calls — no limiter needed.
- **Core guarantee touched?** Yes — this feature *is* the app's core guarantee, already named in `docs/CONVENTIONS.md`'s golden rule: "every number on screen is traceable" to a named, documented assumption, and overrides must actually be used in the calculation. Per engineering standards section 7, this requires automated tests in `test/calc.test.mjs` covering: a known worked example (the one in `docs/research/assumptions.md`) produces the expected quantities; changing a wastage % or a price changes the result; and invalid input (bad floor count, zero-width room, out-of-range wall height) throws a plain-English error rather than returning NaN.

## Done when (a non-developer can check this)

- [ ] Opening `index.html` by double-clicking it (no internet, no server) shows the input form.
- [ ] I can add a few rooms with lengths and widths, set floors and wall height, and press Calculate, and get non-zero numbers for blocks, steel, and concrete.
- [ ] I can instead tick the "approximate size" shortcut, type a m² number, and see a generated room list appear that I can edit before calculating.
- [ ] Every result line shows its own wastage % box, and changing that box changes the number immediately.
- [ ] There is a price table with a price per block, per tonne of steel, and per m³ of concrete, each showing a date and a source, and I can type my own number over any of them and see the OMR total change.
- [ ] Typing something silly (negative room size, 10 floors) shows me a plain-English message, not a blank page or an error I don't understand.
- [ ] The page still works if I turn my WiFi off before opening it.
- [ ] The page looks usable both on my phone and on a laptop screen.
- [ ] The "How this page was built" section is visible further down the same page.

## Open questions (my suggested defaults — proceed unless told otherwise)

1. **Do all floors share the same room list, or can each floor differ?** Suggested default: v1 assumes every floor repeats the same room list the user enters once (simplest to build and matches most small villas); a later version could add "different layout per floor." 
2. **What happens to the auto-generated room list from the m² shortcut — is it just a starting point the user edits, or does changing it back to a plain m² number regenerate and discard edits?** Suggested default: it's a one-time starting point; once generated, the user edits it like any manually-typed list, and there's no "regenerate" button in v1 (avoids losing edits by surprise).
3. **Should the price table let the user pick a currency other than OMR?** Suggested default: no — OMR only in v1, since this is for an Oman/GCC self-builder audience per the researcher's brief; a currency switch is easy to add later if asked.


## Amendment (after code review, 2026-09-22)

Wastage is per material (blocks, concrete, rebar), not per element — three named assumptions, edited in the assumptions panel; the breakdown table shows them read-only. Assumptions that do not drive v1 maths are shown read-only as "reference only".
